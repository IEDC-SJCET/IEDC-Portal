## Prerequisites

Ensure the following are installed before you begin:

| Tool | Version | Notes |
|---|---|---|
| Node.js | 20+ | [nodejs.org](https://nodejs.org) |
| Bun | Latest | [bun.sh](https://bun.sh) — preferred package manager |
| Git | Any recent | — |

You will also need accounts or access to:

- **Supabase** — PostgreSQL database (free tier is sufficient for development)
- **Google Cloud Console** — OAuth 2.0 client credentials for sign-in

## Getting Started

### 1. Fork and clone

Fork the repository on GitHub, then clone your fork locally:

```bash
git clone https://github.com/<your-username>/IEDC-Portal.git
cd IEDC-Portal
```

Add the upstream remote so you can pull in future changes:

```bash
git remote add upstream https://github.com/IEDC-SJCET/IEDC-Portal.git
```

### 2. Install dependencies

```bash
bun install
```

### 3. Configure environment

Copy the example environment file and fill in your values:

```bash
cp .env.example .env
```

See [Environment Variables](#environment-variables) for a description of each variable.

### 4. Set up the database

Push the Drizzle schema to your Supabase database:

```bash
bun run db:push
```

### 5. Start the development server

```bash
bun run dev
```

Open [http://localhost:3000](http://localhost:3000). The app hot-reloads on file changes.

## Environment Variables

All required variables are documented in `.env.example`. The table below summarises each one:

| Variable | Required | Description |
|---|---|---|
| `NEXT_PUBLIC_APP_URL` | Yes | Base URL of the app (e.g. `http://localhost:3000`) |
| `DATABASE_URL` | Yes | Supabase PostgreSQL connection string |
| `NEXT_PUBLIC_SUPABASE_URL` | Yes | Your Supabase project URL |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Yes | Supabase anon/public key |
| `BETTER_AUTH_SECRET` | Yes | Random secret — generate with `openssl rand -base64 32` |
| `BETTER_AUTH_URL` | Yes | Same as `NEXT_PUBLIC_APP_URL` |
| `ALLOWED_STUDENT_DOMAIN` | Yes | Email domain students must register with (e.g. `@sjcetpalai.ac.in`) |
| `GOOGLE_CLIENT_ID` | Yes | Google OAuth client ID |
| `GOOGLE_CLIENT_SECRET` | Yes | Google OAuth client secret |
| `QR_GLOBAL_PEPPER` | Yes | Random hex string for QR security — generate with `openssl rand -hex 32` |
| `UPSTASH_REDIS_REST_URL` | No | Upstash Redis URL (leaderboard caching; works without it) |
| `UPSTASH_REDIS_REST_TOKEN` | No | Upstash Redis token |
| `RESEND_API_KEY` | No | Resend API key (emails log to console if omitted) |
| `EMAIL_FROM` | No | Sender address for outgoing emails |

> **Never commit `.env` to version control.** It is already listed in `.gitignore`.

## Database Setup

This project uses **Drizzle ORM** against a **Supabase PostgreSQL** database.

| Command | Description |
|---|---|
| `bun run db:push` | Push the current schema to the database (no migration file) |
| `bun run db:generate` | Generate a new SQL migration from schema changes |
| `bun run db:migrate` | Apply pending migrations |
| `bun run db:studio` | Open Drizzle Studio — a GUI for browsing and editing data |
| `bun run db:set-role` | Assign a role to a user manually |

**When to use `db:push` vs `db:migrate`:**
- Use `db:push` while iterating locally on a feature branch — it skips migration files and is fast.
- Use `db:generate` + `db:migrate` when you are ready to ship schema changes that need to be tracked and applied in order on other environments.

## Development Workflow

1. **Sync with upstream** before starting any new work:
   ```bash
   git fetch upstream
   git rebase upstream/main
   ```

2. **Create a feature branch** from `main`:
   ```bash
   git checkout -b feat/your-feature-name
   # or
   git checkout -b fix/short-description
   ```

3. **Make your changes** in small, focused commits (see [Commit Message Format](#commit-message-format)).

4. **Lint before pushing**:
   ```bash
   bun run lint
   ```

5. **Push your branch** and open a Pull Request against `main`:
   ```bash
   git push origin feat/your-feature-name
   ```

### Branch naming

| Prefix | When to use |
|---|---|
| `feat/` | New feature |
| `fix/` | Bug fix |
| `refactor/` | Code cleanup with no behaviour change |
| `docs/` | Documentation only |
| `chore/` | Build, config, or dependency changes |
| `hotfix/` | Urgent fix that needs to go directly to production |

## Code Style & Conventions

- **TypeScript everywhere.** Avoid `any`; prefer explicit types and Zod schemas at system boundaries.
- **Linting.** The repo uses ESLint with the Next.js config. Run `bun run lint` and fix all errors before opening a PR. No warnings are acceptable in new code.
- **Formatting.** There is no auto-formatter configured — match the style of the file you are editing (2-space indentation, single quotes for strings in TSX, no trailing semicolons is the prevailing style in this repo).
- **No dead code.** Remove unused imports, variables, and commented-out blocks before committing.
- **No console statements** in production paths. Use server-side logging or remove debug statements.
- **Components.** Keep components in `src/components/`. Page-specific components that will not be reused elsewhere may live co-located inside `src/app/`.
- **Server vs. client.** Default to Server Components. Add `"use client"` only when the component requires browser APIs, event handlers, or client-side state. Keep client bundles small.
- **API routes.** All API handlers live under `src/app/api/`. Return consistent JSON shapes. Validate request bodies with Zod.
- **Database.** All DB access goes through the Drizzle client in `src/db/`. Do not write raw SQL outside of migrations.
- **Auth checks.** Every protected route and API handler must verify the session and the user's role. Never trust client-supplied role claims.

## Commit Message Format

This project follows [Conventional Commits](https://www.conventionalcommits.org/). Each commit message must have the form:

```
<type>(<optional scope>): <short summary>

[optional body]

[optional footer]
```

### Types

| Type | When to use |
|---|---|
| `feat` | A new feature visible to users |
| `fix` | A bug fix |
| `refactor` | Code change that neither fixes a bug nor adds a feature |
| `perf` | A change that improves performance |
| `docs` | Documentation changes only |
| `test` | Adding or fixing tests |
| `chore` | Build process, dependency, or tooling changes |
| `revert` | Reverting a prior commit |

### Examples

```
feat(events): add CSV export for attendance records

fix(leaderboard): correct tie-breaking when points are equal

refactor(student): centralise data fetching with TanStack Query

chore: upgrade drizzle-kit to 0.31.10
```

**Rules:**
- Use the imperative mood in the summary line ("add", not "added" or "adds").
- Keep the summary under 72 characters.
- Reference relevant issue numbers in the footer: `Closes #42` or `Refs #17`.
- One logical change per commit. Split unrelated changes into separate commits.

## Submitting a Pull Request

1. **Open an issue first** for any non-trivial change — a new feature, a breaking refactor, or a schema change. Discuss the approach before writing code. Small bug fixes and typo corrections do not need an issue.

2. **Fill out the PR template.** Describe *what* changed and *why*. Link the related issue with `Closes #<number>`.

3. **Keep PRs focused.** A PR should do one thing. Reviewers should be able to understand its scope from the title alone.

4. **Self-review your diff** before requesting review. Check for leftover debug code, commented-out blocks, and unintentional changes.

5. **Ensure CI passes.** `bun run lint` and `bun run build` must succeed.

6. **Respond to review comments** promptly. If you disagree with a suggestion, explain why; do not silently ignore it.

7. **Do not force-push** to a branch that is already under review unless asked to. Use a new fixup commit instead.

### PR title format

Follow the same Conventional Commits style as commit messages:

```
feat(certificates): support landscape orientation in custom templates
fix(auth): prevent redirect loop on expired session
```

## Issue Etiquette

- **Search before filing.** Check if the issue already exists (open or closed) before creating a new one.
- **One issue per problem.** Do not bundle unrelated bugs or requests.
- **Bug reports** must include: steps to reproduce, expected behaviour, actual behaviour, and the environment (OS, browser, Node version).
- **Feature requests** must include: a clear description of the problem you are solving and why the existing behaviour is insufficient.
- **Be respectful.** Treat maintainers and other contributors as you would like to be treated. Dismissive or demanding language will result in the issue being closed.
